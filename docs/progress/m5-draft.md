**목표:** 하루 출석 시나리오(시나리오 B)를 펫이 대신 지켜본다. 사용자가 직접 로그인한 숨김 LMS 창에서 출석 상태를 읽고, 마감 30분 전부터 알린다. 출석 버튼은 사용자가 직접 누른다.
**데모:** 하루 출석 시나리오 (경계 시각을 흉내 내 `NeedStart → StartOverdue → Studying → NeedEnd → Complete` 순환 + 실제 하루)

## 먼저 알아 둘 사실: 호스트에 창 기능이 아직 없다

SDK v1(`packages/plugin-sdk/src/v1/contracts.ts`)에는 `windows.create`, `getJson`, `onResume`, `openExternal`이 선언돼 있지만, 호스트는 창 기능을 구현하지 않았다.

- `packages/plugin-host/src/session.ts:466-479`: `windows.create`는 옵션·권한 검사 뒤 `E_UNAVAILABLE ("창 기능은 아직 사용할 수 없습니다")`을 던지고, `window.show`·`window.hide`·`window.getJson`은 바로 `E_UNAVAILABLE`이다.
- 따라서 `jungle`의 핵심인 "숨김 LMS 창에서 GET 조회"가 되려면 **호스트 기능(체커 창)을 먼저 만들어야 한다.** SDK 계약(v1)은 이미 있어 수정이 필요 없을 것으로 보이나, 호스트 구현이 `packages/plugin-host/` 권한·창 검사를 건드리므로 **머지 전 gate 대상**이다.
- 이 때문에 규모는 기획안의 M(중)보다 커질 수 있다. 결정 1로 알림 품질까지 포함하게 되어 **3단계로 나눈다** (1단계 호스트 창·판정, 2단계 jungle 알림·운영, 3단계 알림 품질).

### 3단계: 알림 품질 (결정 1로 추가, 2026-10-08)

2단계까지 끝난 뒤 진행한다. 3단계는 `jungle`과 독립이라 앞 단계가 막혀도 따로 진행할 수 있다. 근거는 M4 실사용에서 사용자가 겪은 불편이다 (`backlog.md` 2026-10-07 항목 3건).

| # | 완료 기준 | 검증 |
|---|---|---|
| 14 | hook 알림이 구체적이다: 폴더 이름 외에 시킨 일(마지막 프롬프트 첫 줄), 결과(마지막 응답 요약), Notification `message`가 말풍선 한 줄(약 80자)과 `--detail`에 담긴다. 언어모델 없이 규칙 기반으로 자른다. Claude Code·Codex payload 필드는 구현 전에 실제 덤프로 확인한다 | A + H |
| 15 | 펫 어투: 캐릭터 팩에 상황별(완료·대기·실패 등) 문구 템플릿을 두고, 작업명·결과 같은 슬롯을 채워 알림 문구에 적용한다. 언어모델 없이 정해진 템플릿만 쓰고, 템플릿이 없으면 기본 문구로 돌아간다 | A + H |
| 16 | reminders 설정이 덜 헷갈린다: 시각이 24시간제임을 안내하거나 입력을 검증하고, 다음 알림 시각을 표시하며, 형식 오류로 건너뛴 규칙을 화면에 보여 주고, 저장하지 않은 변경을 표시한다 | A + H |

**주의:**
- 15번은 캐릭터 매니페스트에 어투 필드를 추가해야 할 가능성이 크다. 매니페스트 스키마가 M0 계약이면 변경에 ADR과 사용자 확인이 필요하다. `packages/plugin-sdk/src/v1/`은 수정 금지이므로, 필드 위치(캐릭터 팩 vs 앱 설정)를 먼저 설계해서 계약을 건드리지 않는 쪽을 우선 검토한다.
- 14·15번은 데이터 슬롯을 공유한다(14가 작업명·결과를 만들고 15가 템플릿에 채운다). 같이 설계하고 한 task 묶음으로 진행한다.
- reminders의 "독립 스케줄링 기능으로 승격"은 이번에 넣지 않는다 (16번은 UI 개선까지만).
- Orca 연동은 M6로 둔다.

## 결정 현황 (사용자, 한 번에 하나씩 묻는다)

1. **M5 범위 — 결정됨(2026-10-08): `jungle` + 알림 품질.** 호스트 창 기능이 새로 필요해 이미 범위가 크므로, 3단계로 나누고 마일스톤 소모량을 단계마다 기록해 한도 경고(16-5장)를 놓치지 않는다.
2. **실사용 기간 — 결정됨(2026-10-08): 1일로 단축.** 기획안 1주에서 줄인 것이라 동결 때 `decisions.md`에 근거를 남긴다. 단축으로 약해지는 증거(주말 경계, 여러 번의 잠자기 복귀, 마감 놓침 빈도)는 기준 9의 가짜 시계 테스트와 중간 플레이 테스트(6)로 보완한다. 아래는 결정 전 원문이다: **실사용 기간**: 기획안 기준 1주(기준 13)를 그대로 둘지, M4처럼 줄일지. 출석 마감은 놓치면 손해가 분명해서 1주를 유지하는 쪽을 제안한다.
3. **이용 조건 확인(H) — 방식 결정됨(2026-10-08): 사용자가 직접 확인.** LMS의 비공식 내부 API를 읽는 방식이 이용 조건에 어긋나지 않는지 사용자가 정글 이용 약관·공지를 보고 결과를 알려 준다. 설계는 Jungle Bell이 같은 방식을 쓴다는 점을 근거로 하지만, 이 저장소에서 확인된 사실이 아니다.
   - **게이트:** 확인 결과가 `docs/progress/`에 기록되기 전에는 실제 LMS를 호출하는 작업(기준 6의 실제 로그인·응답 확인, 기준 7·8의 실호출)을 시작하지 않는다. 호스트 창 구현(1·2), 판정 로직(3), 3단계(알림 품질)는 이 확인과 무관하게 먼저 진행할 수 있다.
   - **어긋나면:** 2단계의 `jungle` 기준(7–13)을 접고 3단계(알림 품질)만 M5로 진행한다. 호스트 체커 창은 다른 플러그인에 쓸 수 있어 남긴다.
   - 사용자는 확인한 날짜와 결론(허용 / 불허 / 불명확)을 한 줄로 알려 주면 된다. 불명확하면 운영진 문의로 바꾼다.
4. **로그인 일정 — 결정됨(2026-10-08): 1단계 중 호스트 창 구현(기준 2) 직후.** 체커 창과 `getJson`이 동작하면 바로 한 번 직접 로그인해 실제 응답 구조를 확인하고, 기수 선택과 필드명을 확정한다(기준 6). 판정 로직(3)은 아직 초기라 필드명이 달라도 고치기 쉽다.
   - **선행 조건:** 결정 3의 이용 조건 확인 결과가 기록돼 있어야 한다. 기준 2가 끝났는데 확인이 안 됐다면 그 task 뒤에서 멈추고 사용자에게 알린다(다른 task는 계속).
   - **사용자가 할 일:** 앱의 로그인 창에서 직접 로그인한다(비밀번호는 앱이 저장하지 않는다). 응답 확인은 coordinator가 상태 값만 읽고 본문·쿠키는 기록하지 않는다(기준 11).
