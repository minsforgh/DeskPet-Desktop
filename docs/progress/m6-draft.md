# M6 초안 (2026-10-08, 사용자 결정: 3단계 — 팩 + reminders + 소항목)

> `/milestone-start 6` 에서 이 초안을 완료 기준으로 구체화해 사용자 확인 후 동결한다. 동결 전에는 task 를 만들지 않는다. 시작 전에 직전 마일스톤(M5)의 "판단"이 기록돼 있음(계속, 2026-10-08).

## 범위 결정 근거

- 백로그 열린 항목 11개를 합치면 L 4개 + M 2개 + 소항목이라 M5 의 약 2.5~3배다. 전부 넣으면 기획안 16-5 의 "소모량 1.5배 초과" 신호가 시작부터 걸리고, 사용자 입력(UX 피드백·아트·gate 승인)이 병목이 된다. 그래서 단계를 나눠 일부만 M6 에 담는다.
- A(팩 에셋)는 B(reminders)·C(보조 펫)의 기반이라 먼저 한다. 어투·상호작용의 저장 위치(D-037 Q9)가 팩으로 옮겨지기 때문이다.

## 단계

| 단계 | 내용 (백로그 항목) | 규모 | 사용자 입력·gate |
|---|---|---|---|
| 1단계 기반·소항목 | G 단일 인스턴스 잠금 · H 어투를 jungle·reminders 에도 적용(D-033 종류 준비됨)·직접 누른 상호작용이 방해 금지에 막히지 않게·지금 확인 연타 시 말풍선 중복 정리 · K e2e 동시 실행 간섭 원인 조사·기준 밖으로 머지한 기능을 기획안에 명시 · A 로더·검증(extends 병합, 확장 매니페스트, `interactions.json` 파서, 안전한 쓰기) | M | `packages/core` 변경(계약 테스트). 기획안 갱신은 사용자 승인 |
| 2단계 사용자 체감 | A 사용자 팩 폴더·선택·복제·삭제 + 편집기 UI(어투 인라인 편집·미리보기·순서 이동·슬롯 삽입, 상호작용 편집)와 settings.json 상호작용 → 팩 이전(InteractionStore 구현체 교체) · B reminders 설정 UX 개편 | L | **B 는 사용자가 헷갈린 점을 먼저 모아야 설계 가능.** main IPC 추가(설정 창 허용 채널 목록) |

## M7 이후로 미룬 것

E cron 5필드(plugin-host gate) · F 로컬 HTTP 토큰 확인·재발급(event-server gate) · I `/today`·`/weekly` Orca 예약 실행(습관이 잡힌 뒤) · J 기획안의 `orca` 플러그인 · 3단계에서 고르지 않은 C 또는 D

## 이미 결정된 것 (다시 묻지 않는다)

- ADR-0007 1단계: 폴더 + 파생 팩 먼저, `extends` 는 내장 팩만, 복제는 항상 파생, 편집 범위는 어투·상호작용·메타 + 재생 설정(그림 시트 제외), 상호작용은 팩의 `interactions.json` (D-037).
- 어투는 코딩 에이전트 알림에 적용 중이고 종류 7종 준비됨(D-030·D-033). jungle·reminders 적용은 M6 1단계 H.
- reminders 개편은 M5 기준 16 이월(D-038).

## 시작 전에 필요한 것

1. 사용자: reminders 에서 헷갈린 점을 한두 줄씩(규칙 추가·편집 흐름, 시각·요일 입력, 다음 알림 표시, 저장·적용 피드백 등) — 2단계 B 의 설계 입력.
2. 사용자: 3단계로 C 와 D 중 무엇을 할지(2단계가 끝난 뒤 정해도 됨). C 면 치비 아트 제작 계획.
3. 계획과 기준 동결은 Opus 로(`/milestone-start` 는 Opus 스킬). Claude 주간 76%(리셋 10/10 02:00)라 리셋 뒤가 안전하다. 구현 worker 는 Codex 로.

## 위험

- A 의 `extends` 병합 규칙이 커져 계약이 불안정해질 수 있다 → 병합 결과도 기존 `validateCharacterManifest` 를 통과하게 하고 덮어쓰기 범위를 ADR-0007 4-3 표로 제한.
- reminders 개편이 "독립 스케줄링 기능 승격"으로 번질 수 있다 → M6 은 UX 개편까지만, 승격은 백로그에 남긴다.
- 기준 밖 요청이 또 늘 수 있다 → 동결 후 추가는 backlog 로, 사용자가 명시 지시한 것만 예외로 기록한다.
