# 판단과 검증을 바꾼 사례

DeskPet의 핵심 관찰은 **에이전트가 작업을 완료하고 테스트가 통과해도, 사용자가 기대한 결과는 없을 수 있다**는 점입니다. 이 문서는 당시 기록에서 확인되는 선택·수치와 현재 코드의 검증 근거를 연결합니다.

아래의 수치는 기존 개발 기록을 다시 정리한 것입니다. 이번 문서 보강 중 성능을 새로 측정하지 않았습니다. 원본 운영 DB·대화는 비공개이고, 과거 커밋은 이 공개 사본에 없으므로 당시 경위를 독립 검증하는 데는 한계가 있습니다.

## 1. 빠른 감지 테스트는 통과했는데 알림은 늦었다

### 관찰과 변경

2026-10-15, 실제 Orca에 Run 18개가 쌓인 환경에서 게이트를 만들자 알림이 약 32초 뒤에 나타났습니다. 앱이 상태를 한 번 읽는 데 22.4초가 걸렸고 CLI 명령 한 번은 약 0.35–0.4초였습니다. 테스트의 가짜 CLI는 Run 1개·즉시 응답이어서 이 조건을 다루지 못했습니다.

기존 빠른 감지 신호만으로는 긴 읽기 작업을 없앨 수 없었습니다. 변경은 읽기 비용에 집중했습니다. 빠른 읽기에서 끝난 Run을 재사용하고 Run별 읽기는 최대 4개씩 병렬로 진행했습니다. 30초 전체 확인은 안전망으로 유지했습니다.

| 측정 구간 | 변경 전 기록 | 변경 후 기록 | 읽을 때 주의할 점 |
|---|---:|---:|---|
| 전체 스냅샷 읽기 | 22.4초, CLI 57호출 | 7.7–10.8초 | 전체 상태를 읽는 시간끼리 비교 |
| 빠른 읽기 | 별도 값 미기록 | 2.9–3.3초 | 전체 읽기 22.4초와 같은 작업으로 비교하지 않음 |
| 게이트 생성 → 말풍선 | 약 32초 | 3.5초 | 실제 사용자 결과의 관측값. 스냅샷 시간과 별개 |
| 테스트 조건 | Run 1개·즉시 응답 가짜 | 여러 Run·명령 지연을 가진 가짜와 실제 CLI 측정 추가 | 가짜 통과만으로 지연 기준을 닫지 않도록 변경 |

측정 조건은 같은 PC의 실제 Orca Run 18개입니다. 게이트 관측은 같은 날 14:12와 15:06 기록을 대조했습니다. 반복 횟수·분산·당시 PC 부하와 Run 상태를 완전히 통제한 대조 실험은 아니므로, 일반적인 배속이나 생산성 향상률로 환산하지 않습니다.

### 근거와 역할

- 당시 관측: [M12 데모](progress/demo/m12-orca-and-lines.md), [마일스톤 M12 기준 4](progress/milestones.md).
- 현재 코드: [OrcaReader](../packages/plugin-host/src/orca-reader.ts)의 `MAX_PARALLEL_RUNS`, quick 읽기·Run 재사용 경로.
- 현재 테스트: [orca-reader.test.ts](../packages/plugin-host/src/orca-reader.test.ts)의 quick 읽기·병렬 읽기 검증, [orca.e2e.test.ts](../apps/desktop/e2e/orca.e2e.test.ts), [orca-wire.e2e.test.ts](../apps/desktop/e2e/orca-wire.e2e.test.ts).
- 기록된 역할: 실사용에서 드러난 문제를 수정 작업 A4로 연결했고, 구현은 에이전트가 담당했습니다. 마일스톤 기록에는 사용자가 끝난 Run 건너뛰기·병렬 읽기 방향을 결정하고 실제 알림을 재확인한 것으로 남아 있습니다. 원인 분석·대책 제안·구현에 참여한 AI와 제작자의 선택·확인을 구분합니다.

이 사례의 학습은 외부 도구의 데이터 규모·호출 지연을 테스트에 반영하는 것입니다. 측정한 개선 범위는 앱의 상태 조회와 알림 지연입니다.

## 2. 내부 배지 값은 있었지만 화면에는 없었다

같은 M12 실사용에서 배지 값이 `/status`·개발 제어 상태에는 있으나 화면에는 그려지지 않는 결함이 드러났습니다. 기존 테스트는 내부 값을 확인했기 때문에 통과했습니다.

| 확인 대상 | 변경 전 | 변경 후 |
|---|---|---|
| 승인 대기 표시 | 상태에 배지 값 존재 | 펫 칩·툴팁·트레이에 표시 |
| 완료 기준의 증거 | 내부 상태 값 일치 | 렌더러 요소의 보임·문구·좌표, 사용자 재확인 |
| 사용자 액션 | 트레이 다시 보기 제공, 펫 화면에는 지속 표시 없음 | 칩 클릭으로 버튼 있는 말풍선 다시 보기, 처리 뒤 건수 감소 |

현재 [plugin-badge.e2e.test.ts](../apps/desktop/e2e/plugin-badge.e2e.test.ts)는 렌더러가 보고한 배지 경계·간격·화면 내 위치를 확인하고 내장 wolf-maid 사본도 사용합니다. [orca.e2e.test.ts](../apps/desktop/e2e/orca.e2e.test.ts)는 Orca 알림 흐름을 다룹니다. 이 문서 보강에서 해당 테스트를 새로 실행한 것은 아니며, 공개 전 실행 범위는 [VALIDATION](VALIDATION.md)과 구분합니다.

![수정 후 배지 렌더링 예시](progress/demo/m12-badge-chip.png)

이미지는 수정 후 e2e 테스트 플러그인으로 캡처한 렌더링 예시입니다. 실제 Orca 연동의 당시 사용자 확인은 [M12 데모](progress/demo/m12-orca-and-lines.md)의 5·6단계에 따로 기록되어 있습니다.

이후 [AGENTS.md](../AGENTS.md)에 화면 완료 기준은 렌더러가 그린 결과를 확인하고, 외부 CLI 가짜는 실제 규모·지연을 반영하도록 명시했습니다. 실패를 해당 기능의 수정뿐 아니라 다음 worker의 검증 조건으로 옮긴 사례입니다.

## 3. 제작자가 무엇을 결정했는가

AI가 제안·구현한 부분과 제작자의 판단을 구분하기 위해 결정 기록에 명시된 사례를 골랐습니다. 아래 설명은 그 기록의 요약이며 당시 대화의 재구성이 아닙니다.

| 상황 | 기록된 제작자의 선택 | AI가 담당한 부분 | 근거 |
|---|---|---|---|
| 자동 검사는 평문이 같다고 했지만 대사 구조가 `LMS 로그인이 / 풀렸어요`처럼 나뉨 | 앞말은 호칭·부름, 끝말은 독립된 맺음말만 분리하고 주어·서술어는 나누지 않도록 규칙 결정 | coordinator 검토에서 문제 정리, worker가 데이터 재작업·전후 표 작성 | D-076, [대사 전후 표](progress/demo/m13-lines-split.md) |
| 실제 어투 편집 저장이 `voice.json`의 구조·`lines`를 지움 | 개발자 모드의 제자리 편집은 유지하고, 편집한 값·다른 키를 보존하는 저장으로 고치도록 결정 | 기존 파일을 읽고 `templates`만 교체하는 구현, 내장 팩 사본 검증·복원 | D-078, [M13 기준 7](progress/milestones.md) |
| M13 종료 후 다음 작업을 정할 때 백로그 검토가 빠짐 | 누락을 짚고 오케스트레이션 보강·검증 안정화를 다음 마일스톤으로 먼저 진행. 다른 기능은 뒤로 미룸 | coordinator가 개선 항목·명세를 정리하고 workers가 구현 | D-079·D-080·D-081, [결정 기록](progress/decisions.md) |

대사 구조의 전후는 다음처럼 읽을 수 있습니다. `/`는 구조의 경계를 설명하는 구분자입니다.

| 항목 | 수정 전 구조 | 수정 후 구조 |
|---|---|---|
| 로그인 해제 문장 | `LMS 로그인이 / 풀렸어요` | `LMS 로그인이 풀렸어요.`를 내용에 유지 |
| 분리 기준 | 같은 평문을 만들 수 있으면 통과 | 각 칸의 역할과 문장의 의미를 사람이 읽어 확인 |
| 다음 작업의 산출물 | 자동 평문 비교만으로는 품질 판단 부족 | 사람이 읽을 전후 결과 표를 요구 |

결정 D-082의 e2e 잠금·실측 기반 제한·단계별 진단은 **worker 추천안을 제작자가 승인한 사례**입니다. 후속 기록에는 실패가 남아 있고 원인별 추가 조사가 이어집니다. 제안·승인·구현·검증을 각각의 역할로 기록합니다.

## 이 자료로 설명할 수 있는 것과 남은 것

실제 앱을 사용하며 AI 결과의 허점을 발견하고, 수정 방향·우선순위를 결정하고, 검증 규칙을 다음 작업에 적용한 흐름을 설명할 수 있습니다. 반면 에이전트 미사용 비교군, 사람의 총 투입 시간, 완전한 비용 집계, M14 개선 후 재측정은 없습니다. 첫 시도 완료율 89%는 이 한계를 대신하지 않습니다.

후속 비교를 한다면 동일한 기간·작업 선정·dispatch 분모를 유지하고 새 기능 규모와 운영 중단 원인을 함께 기록해야 합니다. 작은 표본 하나의 개선을 전체 개발 생산성으로 확대하지 않는 것이 이 실험의 다음 과제입니다.
