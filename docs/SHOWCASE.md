# 멀티 에이전트 오케스트레이션 적용 사례

## 실험 질문

실제 앱을 여러 에이전트로 개발할 때 작업 경계와 검증·승인·자원 사용을 관리할 수 있는가? 테스트를 통과했는데 실사용에서 실패한 경우 다음 작업에 적용할 규칙으로 바꿀 수 있는가?

DeskPet은 이 질문을 관찰할 수 있는 산출물입니다. 동시에 에이전트의 완료·사람 확인 대기를 알려 주어 개발 운영에 다시 사용했습니다.

## 사람·AI·외부 도구의 역할

| 주체 | 역할 | 근거 |
|---|---|---|
| 사람 | 목표와 제약, 범위 변경 승인, 디자인 선택, 실제 사용과 결함 피드백 | [결정 기록](progress/decisions.md), 마일스톤 H 확인 |
| Coordinator 에이전트 | 작업 분해·명세, worker 배정, 통합·검증, 지표·실패 정리 | [작업 안내](orchestration-guide.md), [마일스톤](progress/milestones.md) |
| Worker 에이전트 | 분리된 worktree에서 범위 내 구현·테스트·보고 | [AGENTS.md](../AGENTS.md), 작업 기록 |
| Orca | worktree·터미널·task·dispatch·게이트 실행 기반 | 외부 도구. 이 저장소에서 구현한 오케스트레이터가 아님 |
| DeskPet | 작업 완료·질문·게이트 대기 알림과 사용자 액션 | [Orca 데모](progress/demo/m12-orca-and-lines.md) |

소스와 테스트·설계 문서 작성에 AI가 참여했습니다. 이 사례를 수작업 코딩 실적이나 사람이 모든 코드를 독립 검증했다는 주장으로 제시하지 않습니다. 직접 설명할 핵심은 목표·제약·승인을 어떻게 두었고 기록된 실패를 어떻게 다뤘는가입니다.

전역 orchestrate skill, watcher, 개인 집계 도구 일부는 저장소 밖에서 운영했습니다. 이 저장소만 복제해서 당시 자동화 전체를 그대로 재현할 수는 없습니다. 앱 실행과 공개된 작업 지침은 별도로 제공합니다.

## 사례 1: 내부 상태 테스트가 화면 결함을 놓침

- 관찰: 게이트 배지 값은 상태에 있었지만 화면에 그리는 부분이 없어 e2e가 통과해도 사용자는 배지를 볼 수 없었습니다.
- 변경: 렌더러가 실제로 그린 요소의 보임·문구·위치를 완료 기준으로 삼았습니다. 캐릭터 팩 표시 변경에는 내장 팩 사본 검증도 요구했습니다.
- 의미: 테스트 개수보다 사용자에게 약속한 결과를 검증하는지가 중요했습니다.
- 근거: [M12 데모와 실사용 결함](progress/demo/m12-orca-and-lines.md), [경고 기록](progress/STATUS.md), [AGENTS.md](../AGENTS.md).

## 사례 2: 작은 가짜 CLI가 실제 규모의 지연을 놓침

- 관찰: Run 1개·즉시 응답 가짜에서는 빨랐지만 실제 Run 18개에서는 스냅샷 읽기가 20초 이상 걸렸습니다.
- 변경: 종료된 Run을 읽기 대상에서 줄이고 병렬 읽기를 적용했습니다. 실제 규모·지연을 가진 가짜와 실제 프로그램의 읽기 전용 측정을 추가했습니다.
- 의미: 외부 시스템의 데이터 크기와 호출 지연을 테스트 모델에 넣어야 했습니다.
- 근거: [M12 데모](progress/demo/m12-orca-and-lines.md), [CPU·조건 기록](progress/idle-cpu.md), [마일스톤](progress/milestones.md).

## 사례 3: 병렬 개발과 병렬 e2e 실행을 구분

- 관찰: 여러 worker의 전체 e2e가 겹치며 자원 경합과 타임아웃이 발생했습니다.
- 변경: worker는 바꾼 범위만 검증하고 coordinator가 통합 검증을 수행하도록 했습니다. e2e에 작업 트리 공용 실행 잠금을 추가했습니다.
- 남은 것: 잠금은 중복 실행 방지 대책이며 모든 간헐 실패를 해결했다는 뜻은 아닙니다. Electron 충돌 이벤트 관련 실패 등은 M14에서 조사 중입니다.
- 근거: [동시 실행 설명](e2e-concurrency.md), [실패 조사](progress/m14-e2e-flake.md), [현재 상태](progress/STATUS.md).

## 지표의 한계

229 task·243 dispatch, 첫 시도 완료 약 89%, 재시도 약 11%는 운영 기록 집계입니다. 첫 dispatch 성공이 이후 결함이나 후속 수정이 없었다는 뜻은 아닙니다. 입력 토큰에는 캐시가 포함되어 비용으로 환산하지 않았습니다.

에이전트 없이 개발한 비교군은 없고 사람의 총 투입 시간도 통제해 측정하지 않았습니다. 따라서 속도가 몇 배 빨라졌다거나 비용이 줄었다고 주장하지 않습니다. M14 개선 효과도 재측정 완료 전에는 확정하지 않습니다.

원본 대화·운영 DB는 비공개입니다. [기준선](progress/m14-baseline.md)의 집계와 정의를 제공하지만 독립 재계산에는 한계가 있습니다.

## 짧게 설명할 순서

1. 실제 앱을 개발·사용하며 운영한 실험이라는 목적.
2. 작업 명세 하나와 사람의 결정, worker 결과·검증의 연결.
3. 실패 사례 하나에서 테스트의 허점과 바꾼 규칙.
4. 기준선 지표와 아직 입증하지 못한 것.
5. 실행한 DeskPet에서 보이는 알림 결과.
